# 问题与修复方案：模型目录硬编码导致 API Key 管理关联旧模型

## 基本信息

| 项 | 内容 |
| --- | --- |
| 发现日期 | 2026-09-14 |
| 发现方式 | 用户反馈（设置页「API Key 管理」与「模型」页模型不一致） |
| 环境 | DSH 0.1.5-alpha.2（@deepseek-ai/dsh）；macOS；供应商 deepseek-official |
| 严重程度 | 高（写入生效的默认路由会指向不存在的模型 id，下一次模型请求可能失败） |
| 触发接口 | 设置页「API Key 管理」模型下拉框；Host RPC `models`；默认路由同步 `agentDefaultModel.saveSelection` |
| 异常类型 | 无异常抛出，属于静默数据陈旧（stale id） |
| 异常信息 | 无；表现为模型下拉框长期停留在 `deepseek-v4-flash`，而「模型」页真实模型为 `deepseek-flash` |

## 问题描述

供应商 deepseek-official 的模型目录已由 `deepseek-v4-flash` 更新为 `deepseek-flash`（显示名 DeepSeek-V4.1-Flash），但「API Key 管理」页中各项目的「默认模型 model」仍显示 `deepseek-v4-flash`：

1. 编辑项目时模型下拉框只呈现旧 id，看不到新模型；
2. 切回该项目时 `syncRoute` 会把旧 id 写进默认路由（`~/.dsh/settings.yaml` 的 `agent-default-model.model`），后续模型请求可能以不存在的模型 id 发起；
3. 该问题在项目元数据未显式保存模型 id 时同样出现（此时旧 id 来自 Host 的硬编码回落值）。

## 根因分析

### 直接原因

1. Host 硬编码模型常量：`lib/index.js` 中 `const DEFAULT_MODEL = 'deepseek-v4-flash'`，项目元数据 `DSH_APIK_META` 没有 `model` 字段时，`catalog()` 用它填充每个项目的 `model`；`syncRoute` 也用它兜底。
2. Host RPC `models` 返回硬编码清单：`[{ id: 'deepseek-v4-flash' }, { id: 'deepseek-v4-pro' }]` + `providers: ['deepseek-official']`，与真实模型目录无关。
3. Client 初始状态硬编码：部署版 `useState(['deepseek-v4-flash', 'deepseek-v4-pro'])`；动态版 `host.call('models')` 读到的正是上面那份硬编码清单。
4. Client 供应商/模型目录的取数接口在 DSH 0.1.5-alpha.2 已不存在：部署版通过 `ctx.get('connection').api` 调用 `llm.providers({})` 与 `settings.describe({})`。0.1.5 的客户端 `connection` 服务句柄只暴露 `rpc` / `generation` / `state` / `start` 等成员（`dsh-client-connection` 客户端半区 `ctx.provide("connection", handle)`），没有 `api` 属性；客户端远程能力改由 `ctx.remote.<namespace>.<method>()` 提供（`llm/listProviders`、`llm/listConfigurableProviders`、`settings/describe`）。因此 `catalogApi` 恒为 `null`，`fetchCatalog()` 恒返回空数组，模型下拉框只能显示 Host 传来的旧值。

### 产生路径

```
模型目录换代（deepseek-v4-flash -> deepseek-flash）
  -> Host DEFAULT_MODEL 仍为旧 id（meta 无 model 字段时作为回落值）
  -> collectStatus 把旧 id 作为 profiles[].model 下发
  -> Client fetchCatalog 因 connection.api 缺失返回空数组
  -> 下拉框仅显示 profiles[].model（旧 id）
  -> switchProfile -> syncRoute 写入旧 id 作为默认路由
```

### 影响范围

- 「API Key 管理」页所有未显式保存模型的项目的模型展示与保存值；
- 默认路由 `agent-default-model`（供应商 + 模型）被写入失效模型 id 的风险；
- 模型换代（改名、下线）后需要改代码才能跟随，无法自我修正。

## 修复方案

### 方案选择

以 Host 为唯一事实源，实时解析模型目录与默认路由，Client 只渲染 Host 下发数据：

1. Host 新增实时模型目录 `liveCatalog()`：供应商取自 `llm.listProviders()`（已挂载路由）与 `llm.listConfigurableProviders()`（可配置目录），模型取自对应 `settings` 命名空间在 `settingsPath` 处的 `models` 数组（与「设置-模型」页同源），并对已挂载但未声明目录的供应商用 `llm.listModels(provider)` 兜底；结果缓存 5 秒（`CATALOG_TTL_MS`），避免每次状态读取重复解析。
2. Host 默认模型改为实时读取 `agentDefaultModel.currentSelection()`（`liveDefaultRoute()`），彻底删除硬编码模型常量。
3. Host 新增有效路由解析 `effectiveRoute()`：项目配置的模型若不在实时目录中则标记 `stale`，并依次回落到「实时默认路由（同供应商）→ 该供应商首个模型」；`syncRoute` 只写入解析后的有效模型，`collectStatus` 下发 `model`（有效值）、`modelStored`（配置值）、`modelStale`（是否失效）。
4. Host 新增 RPC `catalog`（与 `models` 同义），返回 `providers` / `catalog` / `defaultRoute`；`models` 保留以避免破坏旧客户端。
5. Client 删除 `connection.api` 取数路径与硬编码初始列表，改为从 `list` / `status` / `catalog` 返回的 `catalog` + `defaultRoute` 生成供应商与模型选项；打开编辑器时按实时目录校正 provider 与 model。
6. 目录中只剩真正可用的供应商：已挂载路由，或已被配置出模型目录；未挂载且未配置的声明项（pi-ai 等适配器的休眠路由，实测 41 条）不进入选择列表。

### 不采用的替代方案

| 替代方案 | 不采用原因 |
| --- | --- |
| 只把 `DEFAULT_MODEL` 常量改成 `deepseek-flash` | 下次模型换代（改名或下线）问题复现，需要再次改代码发版 |
| Client 改用 `ctx.remote.llm.listProviders()` 自行读取目录 | 需要把 `remote` 注入链与结果形状适配复制到插件内，且 Host 侧同步默认路由时仍拿不到同一份目录，两个事实源可能不一致 |
| 读取宿主 `~/.dsh/settings.yaml` 文件解析模型目录 | 绕过 settings 服务的内存态与层级合并（schema 默认值、base 层、user 层），且引入文件监听与权限耦合 |
| 静默改写用户元数据里的旧模型 id | 未经用户确认修改配置；改为上报 `modelStale` 并在编辑器提示，用户保存时落盘 |

## 预防建议

1. 插件内不得再出现供应商模型 id 字面量；所有模型信息必须来自 `llm` / `settings` / `agentDefaultModel` 服务。
2. 新增或修改模型相关逻辑时，先在「设置-模型」页确认目录，再核对 `action=catalog` 返回是否一致。
3. 模型换代后按本文「修复后验证点」第 1 至 5 项回归一次。
